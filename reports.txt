## Follow-up gap closure

Every statement below is labelled `VERIFIED`, `INFERRED`, or `UNKNOWN`.

### 1. Underlying cause

- **VERIFIED:** Before the pipeline fix, `build_stream` retired the current
  `StreamPipeline` before opening the replacement. A failed open/seek therefore
  left Rodio attached to a dead ring. The prior pre-fix run recorded `S4
  resume: frames advancing=false (+0)` and `S5 ... Error(Decode)`.
- **VERIFIED:** Before the fix, `SeekMs` only seeded `frames`; it did not call
  the decoder's seek operation.
- **VERIFIED:** Current debug logs show real YouTube media accepted as AAC in a
  progressive MP4, expiry metadata present in the future, HTTP `206` responses,
  requested ranges and byte counts, and decoder readiness with
  `seek_ms=Some(30000)`.
- **INFERRED:** The observed failure was not caused by URL expiry, HTTP 416,
  unsupported Range, or moov placement: no such response/error appeared in the
  failing evidence, while the same live path now returns `206` and decodes.
- **VERIFIED:** The fix addresses both cause and handling: replacement work
  (resolve/open/seek) completes before the old stream is retired, and seeking
  calls `try_seek` on the decoder.
- **UNKNOWN:** A long pause crossing the provider URL expiry boundary was not
  run.

### 3. Cover-art break map

1. **Failing link — artwork allowlist.** Live sidecar search (real anonymous
   provider, 2026-11-04) returns `thumbnailUrl` on
   `yt3.googleusercontent.com` for **20/20 song rows** and **20/20 album
   cards** (videos: `i.ytimg.com` 20/20). `ARTWORK_ALLOWED_HOSTS` listed only
   `i.ytimg.com`, `lh3.googleusercontent.com`, `yt3.ggpht.com`, so
   `fetch_artwork` rejected every catalogue cover, `Artwork` caught the error
   and resolved to `null` → no `<img>` at all. VERIFIED: the real data dir's
   `art/remote` directory did not exist before the fix (no successful fetch
   ever), and contains 126 files after it.
2. **Double conversion.** Queue-mirror rows, library rows and autoplay rows
   store an already-converted `art://localhost/…` URL in `thumbnail`;
   `Artwork` ran `convertFileSrc` again on it, producing a path that
   `serve_art` rejects (not under `art_root`). Fixed by passing resolved
   `art://` URLs through.
3. **Now-playing bar / full-screen player bypassed the cache.** They used
   `nowPlaying.artworkUrl` (raw https) as `<img src>`; the CSP `img-src` has no
   https source, so those two were blocked even when the row image worked.
   Fixed by giving them the same resolver.
4. **Wrong MIME for cached covers.** `fetch_artwork` cached files with no
   extension and `serve_art` labels by extension → `application/octet-stream`.
   Measured: Chromium still renders such an image (naturalWidth 1 in a harness
   page), WebKit is unverified — fixed anyway by caching as `<sha1>.<ext>` from
   the response content type and labelling `webp` in `serve_art`.

### 2. Crash root cause

`apps/desktop/src/shell/Lcd.tsx`: `useArtworkUrl(...)` was called *after* `if (!nowPlaying) return …`. At boot the persisted queue restores from null to playing, so the hook count changed between renders → React error #310 ("Rendered more hooks than during the previous render"), surfaced by React Router's default errorElement as "Unexpected Application Error!". Present in current source, not only a stale bundle: both inventoried copies embedded `index-bDpE6GDw.js`, the same hash the crash trace named.

Verified: with the hook moved back below the early return, `Lcd.test.tsx` fails with exactly `Rendered more hooks than during the previous render.`; with the fix it passes.

Fixes:
- `Lcd.tsx`: hook above the early return.
- `shell/AppError.tsx` (new) + `routes.tsx` `errorElement`: readable crash screen with Reload, Go to Home, Reset UI state (clears only `tansen:`/`bitchord:` keys), Copy details.
- `state/player.ts`: persisted queue carries `v: 1`; `parsePersisted()` discards corrupt/older payloads instead of throwing at boot.
- `main.rs`: `stale_bundled_path()` — a stored `sidecar_jar`/`java_path` that is another build's bundled resource (dev `target/`, trashed `.app`) is replaced by the running bundle's path; a genuine user JDK is kept.
